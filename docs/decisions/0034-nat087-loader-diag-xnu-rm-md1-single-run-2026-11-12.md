With the flag, `Restore environment starting.` is logged and a missing service cache is not fatal. The donor project boots the same way (`rd=md0`, `userland/src/init.c`).
* The kernel must keep rooting on `rd=md1`. XNU's `PE_parse_boot_argn_internal` compares whole keys and the last duplicate wins, so a last token `xrd=md0` is a key of its own and invisible to the `rd` lookup, while `kern.bootargs` (`bsd/kern/kern_sysctl.c`: `strlcpy(buf, PE_boot_args(), BOOT_LINE_LENGTH)`) returns the whole line. ## Known limits disclosed

* The restore-mode route is a reading of Apple's `launchd` (capstone disassembly: the `strstr` import resolved through chained fixups, the predicate at 0x10003b8c8, the flags at 0x10006e8bb/0x10006e8bc, the check at 0x100015c30). Not established: that the flag is set for the substring in this line, that restore mode does not change launchd's job loading (a real restore ramdisk loads its LaunchDaemons, so a job is expected to load, but this is not observed), that no daemon the image starts takes a different branch for `rd=md0`. Whether the restore line lies inside the returned window is unknown (R8 is the honest row if it does not).
* **Restore mode changes what launchd believes about the system**: it is the mode of a restore ramdisk, not of an installed system. The donor project boots this way (`rd=md0`); a later image may need the opposite (real Apple daemons that behave differently in restore mode: for example, daemons that refuse to run when the system is a ramdisk). That question belongs to the run of a larger job set, not to this one.
* **The kernel runs unobserved**, as in decisions 0026-0033. A hang, an abort, a reset or a `SEC_UPLOAD` / automatic restart are possible outcomes. If the phone comes back to Android by itself, the driver's `--restore` is the same restore; Download Mode by keys is the fallback. NAT-051: a debugfs `clk_summary` read once sent this phone through `SEC_UPLOAD`; never repeated.
* Only about 1.61 GiB of the 4 GiB window is free after the reserve. A launchd that survives and runs more uses more of it.
* The returned log is the head and tail of the kernel's buffer (8192 + 32768 bytes). A launchd that stays alive prints more (thousands of lines in a couple of minutes without `/etc/quiet`): the middle may be lost, and then the analyser reports R8 and the gap size instead of a negative. `/etc/quiet` was deliberately not added: it would silence the very lines this run reads.
* A pass says: Apple's launchd entered restore mode on the phone through the command-line substring, skipped the boot tasks that blocked NAT-086 and was alive for at least two job intervals with one job. It does not say that any service other than the job started, that backboardd or SpringBoard can start, or anything about display, input, GPU or the lock screen. The probe is not Apple's launchd and the stage0/init pair is the donor's.
* Host-test evidence: `docs/procedures/nat-087/evidence.json` (the restore reader and ladder run over the REAL NAT-084 and NAT-086 archives and give R5 there, the control that shows the analyser distinguishes launchd with and without the skip; the restore text itself is hand-written because no run has printed it; XNU's real `bootargs.c` and Apple's launchd Boot dictionary are read from the files), `docs/procedures/nat-085/evidence.json`, `docs/procedures/nat-086/evidence.json`, `docs/procedures/nat-083/evidence.json`, `docs/procedures/nat-080/evidence.json`.
