## The question this run answers

> Can the host stream the whole padded root image (2,475,720,704 bytes) over USB bulk-OUT straight into the reserved md1 region before the jump, and does the payload kernel's `/dev/rmd1` then return exactly those bytes to a user process (MMU on, kernel-side read)?

Reported separately: (a) delivery (loader side: NAT-076 engine, NAT-079 receive phase), (b) host-to-device rate, (c) read-back through the kernel (NAT-077 hash probe), (d) whether the DWC3 DMA reaches the reserve above 4 GiB (NAT-040 item U5; the first accepted chunk answers it).

## Sequence

The protocol of decisions 0021-0029 and of `session_nat078.py --image loader-diag-xnu-rx-md1`: gates (this file naming both hashes and decision 0019, the registry incl. NAT-076/077/079/080 done, the udev rule, the collector and companion self-tests, the padded root image size and hash, the device checks, the watcher self-test); one-shot marker; full-image write to RECOVERY (`/dev/block/sda18`) only; full readback; the USB event watcher, the NAT-041 collector (pyusb venv python) and the delivery companion started detached and confirmed (watcher start record, collector poll, companion `loaded` record); one `adb reboot recovery`; the run; then restore of the pinned stock RECOVERY with the NAT-013 tool and the pyusb venv python on a device whose iProduct is `SAMSUNG USB` (never `SEC_UPLOAD`), full-hash readback and an Android check. A failure after the write and before the reboot restores stock and does not reboot. No retry, no second reboot.

What the image does: the loader as in NAT-075 (framebuffer, USB engine, ladder, 4096 MiB window from the DTB, three-span clear, payload copy), with the NAT-076 bulk-OUT engine up behind a 512-byte placeholder destination; `nat079_receive_root`: validate arguments, refuse if host traffic arrived before the destination was real, CPU self-test of 8 pages of the reserve, install the real destination, loop `nat044_tick(); nat047_poll();` until the committed offset equals the size, the 240 s cap, or the engine goes down; pet, flush the log, clean the caches over the window, jump to the payload kernel whatever the receive result was. In the kernel: 16 KiB pages, md0 probe as PID 1, which reads `/dev/rmd1` in 131072-byte chunks and prints a SHA-256 every 128 MiB and at the end, exit status 81; `loader_return()` after 45 s; the loader dumps the console text for the host; the deadline reset to Download Mode.

## Known limits disclosed

* The receive path, the companion, the driver and the probe are host-test only; none has run on this phone. In particular not established: the host-to-phone rate (the 225 s budget needs about 11 MB/s), whether the DWC3 DMA reaches the reserve above 4 GiB (U5), cache visibility of the delivered bytes to the kernel, libusb behaviour when pyusb runs `set_configuration` while the collector polls, whether PID 1 has stdio, how `/dev/rmd1` reads behave, how long a SHA-256 of 2.31 GiB takes on this CPU, and whether the unpetted kernel survives 45 s.
* **The kernel runs unobserved**, as in decisions 0026-0029. A hang, an abort, a reset or a `SEC_UPLOAD` / automatic restart are possible outcomes. If the phone comes back to Android by itself, the driver's `--restore` is the same restore; Download Mode by keys is the fallback. NAT-051: a debugfs `clk_summary` read once sent this phone through `SEC_UPLOAD`; never repeated.
* Only about 1.61 GiB of the 4 GiB window is free after the reserve; the kernel's own use of memory is whatever NAT-075 showed.
* A pass says: a full-size image can be placed in RAM over USB and read back unchanged by a user process of the project's kernel. It does not say that APFS mounts, that the volume is consistent, that dyld or any Apple binary runs, or anything about display or GPU. The probe is not Apple's launchd.
* Deviations from the registry text of NAT-078: the window is 4096 MiB (the loader refuses `mem_size > 4 GiB`), not 4908 MiB; md0 stays the probe ramdisk and the root image goes to the reserve-only `md1`/`rmd1`; the receive phase is direct DMA into the reserve, not staged (README of NAT-079, "Direct versus staged"), so U5 is tested by the first accepted chunk.
* Host-test evidence: `docs/procedures/nat-076/evidence.json`, `docs/procedures/nat-077/evidence.json`, `docs/procedures/nat-079/evidence.json`, `docs/procedures/nat-080/evidence.json`.
