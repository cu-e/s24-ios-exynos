Nineteen daemons whose stderr goes to the console can fill it; the analyser then reports A8 or marks holes instead of claiming a negative. A program in a `ps -A` list is not shown to be healthy.
* `Unable to find persona with type 6` was printed before every spawn in NAT-088 and the heartbeat ran in `user/501`; whether the jobs with `LimitLoadToSessionType` (logd, fseventsd, notifyd, ...) are loadable in that domain is exactly what A4 versus A2 would show. Two plists are disabled while a feature flag is off; the flag state is unknown.
* There is no `launchctl` in this image, so the run cannot ask launchd anything: the heartbeat's `ps -A` and launchd's own lines are the only reporters.
* The kernel runs unobserved, as in decisions 0026-0035: a hang, an abort, a reset or a `SEC_UPLOAD` / automatic restart are possible. If the phone returns to Android by itself, the driver's `--restore` is the same restore; Download Mode by keys is the fallback. A debugfs `clk_summary` read once sent this phone through `SEC_UPLOAD` and is never repeated.
* Only about 1.61 GiB of the 4 GiB window is free after the reserve; nineteen daemons use more of it.
* A pass says: nineteen Apple plists loaded under restore-mode launchd and the seven self-starting daemons were in a process list at the end of the window. It does not say any daemon works, that backboardd or SpringBoard can start, or anything about display, input, GPU or the lock screen. The stage0/init pair is the donor's, not Apple's.
