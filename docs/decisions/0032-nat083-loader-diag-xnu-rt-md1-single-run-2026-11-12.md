> With the delivered APFS image as the kernel's root (`rd=md1`), does the donor boot chain (stage0 → init on the small image) run, do Apple's own `df`, `mount`, `ps -A` and `vm_stat` from that root run to completion on the project's XNU, and what does Apple's `launchd` do as PID 1 after `exec /sbin/launchd.darwin` with an empty job list?

Observables fixed beforehand (all from the kernel/console text that the project's own log chain returns, plus the USB observations): `BSD root:` and `Added memory device md1` lines; `apfs: volume ...` line or its error lines; `stage0:` lines; `=== init: process 1 ...` banner, section headers, `[ ok ]`/`[FAIL]` checks and the summary; `=== /redwood/etc/rc ===` and each `$ command` with its output and any `[exit status N]`/`[killed by signal N]`/`[could not run]` line; the `$ exec /sbin/launchd.darwin` line and every console line after it; the kernel's `initproc ...` / `panic(` text if PID 1 ends; the kernel's free page count; the ending (Download Mode in the cap window). ## Known limits disclosed

* No Apple user-space code has ever run on this phone. The chain stage0 → init has run only as built from the same sources on the host models (IOS-011/012/013 are source-review and host-test). In particular not established: that the donor `apfs` VFS mounts a 2.31 GiB image from RAM on this kernel, that the shared cache and dyld are usable, that the 22 ENOSYS syscalls and the commpage are not hit by these programs, how long Apple's launchd survives without jobs, and how much memory it takes.
* **The delivered image has never been verified as a whole.** NAT-078 read back 59.6% of it correctly and was cut off before the final digest. A corrupted byte beyond that point could show up as an odd failure in rows 1b, 2 or 5; the host's `apfsck` and the companion's per-chunk checksums are the only other evidence. This run does not repair that, and a row 2 or 5 result is therefore not by itself a finding about the kernel.
* **The kernel runs unobserved**, as in decisions 0026-0031. A hang, an abort, a reset or a `SEC_UPLOAD` / automatic restart are possible outcomes. If the phone comes back to Android by itself, the driver's `--restore` is the same restore; Download Mode by keys is the fallback. NAT-051: a debugfs `clk_summary` read once sent this phone through `SEC_UPLOAD`; never repeated.
* Only about 1.61 GiB of the 4 GiB window is free after the reserve. The returned log is the head and tail of the kernel's buffer (8192 + 32768 bytes); the console output of init (checks, `df`, `mount`, `ps`, `vm_stat`) plus the kernel's own lines may exceed that, and then the middle is lost and the analyser reports row 8 instead of a negative.
* A pass says: Apple's userland programs run and Apple's launchd is alive as PID 1 for the run window with no job. It does not say that any service started, that backboardd or SpringBoard can start, or anything about display, input, GPU or the lock screen. The probe is not Apple's launchd and the stage0/init pair is the donor's.
