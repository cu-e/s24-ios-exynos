## Why this image, and its conditions

NAT-093 delivered the root and reached userland, but its log window held one repeated message, so what launchd and the seven self-starting daemons did stayed unobserved. The smallest change that tests whether the window can then show them is to remove the job whose daemon produced the message. It is a measurement design change, not a fix: if another daemon makes the same request, the window fills the same way and the result is A8 again, which is itself information (the kernel's handling of that request is then the blocker, and the remedy is on the kernel side, not in the plist set).

1. **Idle host.** The agent launches only when the host's 1-minute load average is below 6 and no build, test or mutation process of the agent is running (`uptime` and `ps` are checked just before the launch and recorded; strays are stopped by PID). The load seen at launch and the measured delivery rate are reported with the result.
2. **No change to the time rules, the receive phase, the sender or the companion**: receive cap 240 s, `loader_return_after` 60 s, deadline 360 s, as in decisions 0032 to 0036.
3. **A delivery shortfall ends this line.** If the delivery is short of the whole root, the result is inconclusive and decision 0037 is consumed; the same content is not run again on the same terms, because the delivery throughput itself is then the blocker (NAT-091 delivered 91.82% at load ~30; NAT-093 delivered everything at load 3.89).
4. A complete delivery with a result other than A1 is evidence and not a reason to run again.

Eighteen daemons whose stderr goes to the console can fill it; the analyser then reports A8 or marks holes instead of claiming a negative. A program in a `ps -A` list is not shown to be healthy.
* Removing `lsd` is a hypothesis about what filled the window in NAT-093, not an established cure: the message could come from other daemons too, and the 129,137 unsent bytes of that run were never read, so what else the kernel printed is unknown.
* `Unable to find persona with type 6` was printed before every spawn in NAT-088 and the heartbeat ran in `user/501`; whether the jobs with `LimitLoadToSessionType` (logd, fseventsd, notifyd, ...) are loadable in that domain is exactly what A4 versus A2 would show. Two plists are disabled while a feature flag is off; the flag state is unknown.
* There is no `launchctl` in this image, so the run cannot ask launchd anything: the heartbeat's `ps -A` and launchd's own lines are the only reporters.
* The kernel runs unobserved, as in decisions 0026-0036: a hang, an abort, a reset or a `SEC_UPLOAD` / automatic restart are possible. If the phone returns to Android by itself, the driver's `--restore` is the same restore; Download Mode by keys is the fallback. A debugfs `clk_summary` read once sent this phone through `SEC_UPLOAD` and is never repeated.
* Only about 1.61 GiB of the 4 GiB window is free after the reserve; eighteen daemons use more of it.
* A pass says: eighteen Apple plists loaded under restore-mode launchd and the seven self-starting daemons were in a process list at the end of the window. It does not say any daemon works, that backboardd or SpringBoard can start, or anything about display, input, GPU or the lock screen. The stage0/init pair is the donor's, not Apple's.
* Reader v2 infers a lost begin line only under the rules of `docs/procedures/nat-097/README.md`; a capped dump whose final tail record was also lost is refused (the hand reading is then labelled post hoc, as in NAT-093).
* Host-test evidence: `docs/procedures/nat-096/evidence.json`, `docs/procedures/nat-097/evidence.json`, `docs/procedures/nat-092/evidence.json`, `docs/procedures/nat-089/evidence.json`, `docs/procedures/nat-088/evidence.json`; and `docs/procedures/nat-093/evidence.json` (the run whose result motivated this one).
