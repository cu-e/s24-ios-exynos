## Known limits disclosed

* The skip path is a reading of Apple's code in the shared cache and of XNU's `kern_mib.c`. Not established: that the project's XNU (the stand-in AMFI/Seatbelt build with the donor apfs VFS) creates `hw.ephemeral_storage` from the ADT of this phone, that the value 1 is what `os_variant_uses_ephemeral_storage` wants, and that the skip is enough: other boot tasks after `keybag` may need the SEP, a data volume or a keybag too (this is exactly what the run shows). Faking a keybag is out of scope.
* **Ephemeral storage changes what launchd believes about the data volume.** With the property present, Apple's launchd tasks (and any daemon that calls `os_variant_uses_ephemeral_storage`) take their ephemeral-data-volume branches (the branches the code takes for a device whose data volume is ephemeral). This is a different claim from "the phone has an iOS data partition": there is none, `/private/var` is a RAM filesystem.
* **The kernel runs unobserved**, as in decisions 0026-0032. A hang, an abort, a reset or a `SEC_UPLOAD` / automatic restart are possible outcomes. If the phone comes back to Android by itself, the driver's `--restore` is the same restore; Download Mode by keys is the fallback. NAT-051: a debugfs `clk_summary` read once sent this phone through `SEC_UPLOAD`; never repeated.
* Only about 1.61 GiB of the 4 GiB window is free after the reserve (105,521 free pages of 16 KiB were measured in NAT-084 before launchd). A launchd that survives and runs more tasks uses more of it.
* The returned log is the head and tail of the kernel's buffer (8192 + 32768 bytes). In NAT-084 the whole console text was 33,159 bytes with no gap. A launchd that stays alive prints more (the donor job notes say "a few thousand lines in a couple of minutes" with `/etc/quiet` absent): the middle may be lost, and then the analyser reports S8 and the gap size instead of a negative. `/etc/quiet` was deliberately not added: it would silence the very lines this run reads.
* A pass says: keybagd skipped its init on the phone and Apple's launchd was alive for at least two job intervals with one job. It does not say that any service other than the job started, that backboardd or SpringBoard can start, or anything about display, input, GPU or the lock screen. The probe is not Apple's launchd and the stage0/init pair is the donor's.
* Host-test evidence: `docs/procedures/nat-085/evidence.json` (81 tests; the stage reader and ladder run over the REAL NAT-084 archive and give S5 there, the control that shows the analyser distinguishes the cases; the skip text itself is hand-written because no run has printed it), `docs/procedures/nat-083/evidence.json`, `docs/procedures/nat-080/evidence.json`.
