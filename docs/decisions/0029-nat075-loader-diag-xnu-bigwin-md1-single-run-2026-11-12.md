## The question this run answers

Can the NAT-068 chain (loader → payload kernel → md0 probe PID 1 → exit 81 → host receives the text) run with three differences, and what does the kernel say about a second, reserve-only ramdisk? Nothing is transferred to the phone in this run.

1. A **4096 MiB window** instead of 512 MiB. NAT-073 found two 512 MiB limiters (the loader's `MAX_WINDOW`, the payload's `mem_size`), both lifted. The loader refuses `mem_size > 4 GiB`, so 4096 MiB is the cap (the registry text's 4908 MiB is superseded). With `memSize > 1 GiB` the kernel's page size becomes 16 KiB; that has never run on this phone.
2. A **reserve-only `RAMDisk1`** of 2,475,720,704 bytes (the 2,475,712,512-byte APFS volume image of the donor recipe rounded up to 16 KiB) inside the payload's `kernel_end`: an ADT entry and address space, no bytes in the payload, not touched by the loader's clear. The registry text calls this a "big md0"; md0 stays the 16,635-byte probe, so the kernel command line (`rd=md0`) and the probe path are NAT-068's.
3. A **bounded watchdog pet**: every 30 loader-seconds while the 150 s cap has not passed, and once before the jump. `hold_seconds` does not poll it; `mk_hold` after the kernel's return (`loader_return_after=8`) does. The cap (150 s, was 60 s) is the NAT-044 deadline reset to Download Mode.

* **PASS: all four of** (1) the chain verdict is PASS (27 `CK` notes, the kernel's own return, the second dump, `HOLD`, no drop, no exception, as in 0026–0028); (2) `root.outcome == "probe-ran-to-exit"`; (3) the kernel text has `Added memory device md1/rmd1 (...) at ... for 0000000093908000` (the size field is in bytes, as md0's `0000000000008000`; 2,475,720,704 = 604,424 × 4 KiB) next to md0; (4) the return is `cap-reset`: Download Mode (`SAMSUNG USB`) at +165 … +195 s after the reboot request.

## Known limits disclosed

* Host tests and source review only for the new parts: a 16 KiB-page boot over 4 GiB, the watchdog pet on this windowed watchdog, and md1's registration have not run on this phone. The loader's clocks run 0.95–1.0 of host time; the pet interval is in loader seconds.
* **The kernel runs unobserved**, as in decisions 0026–0028. A hang, an abort, a reset or a `SEC_UPLOAD` / automatic restart are possible outcomes. If the phone comes back to Android by itself, the driver's `--restore` is the same restore; Download Mode by keys is the fallback. NAT-051: a debugfs `clk_summary` read once sent this phone through `SEC_UPLOAD`; never repeated.
* A refused reset (read-back mismatch) leaves the watchdog unpetted, so the hardware watchdog still ends the run within 83 s of the last pet (host-tested in `test_model.py`, not hardware-observed).
* A pass says: the payload kernel booted with a 4 GiB window and 16 KiB pages on this phone, ran the project's probe as PID 1, registered a reserve-only second ramdisk, and the loader's cap and pet worked. It does not say that the root volume can be delivered, that APFS mounts, or that Apple's launchd or any Apple userland runs; nothing about the console/display or the GPU. The probe is not Apple's launchd.
