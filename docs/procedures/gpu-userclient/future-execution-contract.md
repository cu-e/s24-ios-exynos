# Future bounded GPU-012 actual experiment

This is a review proposal, not execution authority. GPU-012 is independent
roadmap work and is not a first-console prerequisite. The original source
boundary and host fixture remain frozen. There is no concrete GPU provider,
IOService personality, Metal registration, fake Apple type, hardware result,
completion or retirement claim. Default provider readiness refuses admission.

After independent source/plan review and an explicit root lease, first compile
only the three exact plan commands serially: genuine kernel C++ adapter,
portable policy using the same genuine C++ recipe, and existing C dispatcher
using the genuine C recipe. No archive or link step. Retain every diagnostic
and failed object, inspect only actual ARM64 MH_OBJECT files with the bounded
owned parser, and report actual override/provider symbols, typed allocator
metadata and all unresolved XNU imports without stubs. Missing API/ABI or
allocator diagnostics are evidence, not permission to replace genuine types.

The future caller must be a separately reviewed scoped executor. It must
validate original active GPU-012 owner and literal reservations, a registered
planned actual experiment, a fresh canonical GPU-owned output, the final
source-plan file hash and every command/cwd/source hash. It must load the
accepted shared engine by exact immutable bytes, call
`project_approval(..., executor_path=exact_caller)`, reserve the global budget,
and call shared `run_child(..., budget=budget)` for native commands. It may
release only after verified owned-session cleanup; failures retain evidence
and any unsafe reservation. Do not manufacture 1080-row GPU graphs or claim
one of the ten direct-object shards: the independent component shard is
`gpu-userclient`.

The future root allocation must bind task, original owner, actual experiment,
shard, exact caller hash, final source-plan file path/hash, absent actual output
and one serial compiler. Request 256MiB combined controller/descendant RSS;
512MiB requires explicit separate approval if real measurements justify it.
Keep global six compiler jobs/6GiB project RSS, the 2GiB light-work allowance,
three >=4GiB MemAvailable samples one second apart, 45-second admission window,
120-second per-child and a proposed 600-second whole-experiment deadline,
25ms RSS sampling, Landlock writes only to owned output, and finite verified
cleanup. Pin the reviewed root launcher/watchdog and its cancellation behavior
before execution; AF193 alone must not be represented as a proof that controller
SIGTERM cleans children. Never signal an unrelated process.

Host ASan/UBSan is a separate future admitted phase. Compile the existing C
dispatcher once, link the portable C++ policy and distinct synthetic host
fixture, then run the fixture. The commands are authored in the source plan;
their native host compilers are only hashed, never invoked. Controls cover
authentication/readiness, counts/descriptors/version/selector/sizes/alias,
immutable snapshot despite caller-input mutation, busy/close/death/error and
unknown-quiescence references. The fixture supplies test identities/callbacks,
not Apple headers, kernel vtables or GPU hardware behavior.

The accepted AF193 helper sets RLIMIT_AS to 2GiB, which conflicts with a normal
64-bit ASan shadow reservation. Its fixed environment also has no arbitrary
environment argument. Do not run this proposal through that interface or
assume ASAN_OPTIONS/UBSAN_OPTIONS are forwarded. Use fatal compile-time
sanitizer behavior (`-fno-sanitize-recover=all`) in the proposal; any desired
environment must become an explicit qualified part of a future API.

A future independently reviewed sanitizer process contract can use the
already proven JVM/common precedent of RSS supervision without RLIMIT_AS,
while retaining exact caller/argv/plan/source/runtime pins, finite deadlines,
verified owned-session cleanup, Landlock and global ProjectBudget accounting.
It must qualify the host ELF interpreter, transitive libraries, ASan/UBSan
runtime and search precedence without executing a loader tool main or relying
on unbound host defaults. Include meaningful refusal controls for changed
caller/argv/plan/runtime and stale or absent root allocation, plus cancellation,
deadline and memory-stop cleanup controls. A bad-access negative sanitizer
control must actually fail before treating a clean fixture exit as sanitizer
coverage. The current GPU task does not author or override the shared engine:
any shared API change waits for VM044 ownership release, a separately assigned
and reviewed task, and explicit root allocation.

VM044 budget contention and VM045 compiler-resource namespace are prospective
inputs. Record their final accepted helper/profile once in a new source-plan
freeze before actual execution; do not silently upgrade, rewrite historical
absence bindings, resume old products or relabel old keys. No GPU-specific
resource-root failure is established by the current IOKit recipes, which have
`-nostdinc` and no `-idirafter`. Host tests, target compilation, IOConnect,
guest/native ABI and actual Xclipse hardware remain separate unmeasured gates.
