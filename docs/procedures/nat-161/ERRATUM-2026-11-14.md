# Erratum to NAT-161 (2026-11-14, found while analysing NAT-164)

NAT-161's evidence (`evidence.json`, left unchanged as recorded) and the first version of its README said that the single core was
**about 50% idle** on the idle home screen ("busy share 0.50", `cpu161.py`). **That figure is not a measurement and is withdrawn.**

- `cpu161.py` timed each `ps` snapshot by the last launchd log line before it. The console part of the dump has no kernel
  timestamps, and that line can be far older than the snapshot.
- The heartbeat's `ps` itself took **24.8 s and 5.5 s** to run in NAT-161, and 26.9 s and 8.5 s in NAT-164
  (`SWEET hb: … ps … ms=`). So each process's TIME was sampled somewhere inside windows of that size.
- The same method on NAT-164 gives a "share" of 1.02 (SpringBoard 21.9 s, launchd 7.2 s, …). Neither number can be trusted.
- `ps` taking seconds instead of milliseconds suggests heavy contention on the single core, but that is not established either.

**What stands:**
- the frames159 figures (kernel 5 s statistics): 9.65/s, 25.75 ms in the driver;
- iOS ran at 750×1624;
- grade G0 for `fbscale=2`.

`cpu161.py` now reports `busy_share` only when both `ps` runs took less than 1 s, and null with the reason otherwise.

**Still unknown:** whether the single core is saturated. A valid measurement needs per-core idle time with kernel timestamps,
which the `tl: u` lines of `redwood_cpufreq.c` (boot-arg `cpuload=MS`) give.
