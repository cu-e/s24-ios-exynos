## 3. The chosen channel: an EP0-only "pull monitor"

* **Device**: DWC3 in device mode, high speed, polled, ep0 only. Enumerates as a vendor-specific full device (VID 0x1209, PID 0x0001: the pid.codes test pair, as the sweet engine did; no class, one configuration with no interface endpoints) so no host driver binds to it and libusb can open it without kernel support.
* **Requests** (all vendor, device-to-host unless stated; values are a design, fixed in NAT-041):
  `0x01 GET_INFO` (magic `S24L`, version, `boot_id[16]`, host nonce echo, ring base, ring size, total bytes written, overrun and drop counters, stage, state/exception flag);
  `0x02 READ_RING` (`wValue:wIndex` = 32-bit byte offset into the ever-growing stream, `wLength` ≤ 4096; returns the bytes if still in the ring, otherwise a short reply with the loss recorded);
  `0x03 GET_EXC` (the exception frame: ESR, ELR, FAR, SPSR, SP, x0–x30, stage, the same boot ID; valid flag);
  `0x04 SET_NONCE` (host-to-device, 16 bytes);
  `0x05 PEEK` (reserved: bounded read of physical memory/MMIO; this is what later makes GPU bring-up debuggable, it is specified but implemented only after the text path works).
* **Text** goes into one append-only RAM ring through the loader's existing log call (`loader_log`, the kernel's `e1s_log_append` can be mirrored in a later image); each record is `[seq u32][len u16][kind u8][crc8]` + payload. **Exceptions**: the loader's own vectors and the kernel-return stub (NAT-029/NAT-031 path) fill the exception frame, append a `fault` record, then enter the hold loop that keeps polling the event buffer and answering ep0 until the watchdog resets the phone — the hold loop is the same code as the normal service loop.
* **Host collector** (`s24_logd`): waits unattended for VID/PID, opens it with libusb, sends `SET_NONCE` with a fresh random value, reads `GET_INFO`, pulls `READ_RING` and `GET_EXC` at a fixed rate, and writes NAT-016 JSONL frames through `archive.py` (`boot` marker carrying `boot_id` = host nonce + device boot block, `log`, `stage`, `fault`, `drop`, `end` on disconnect). A reset without USB disconnect is detected by the nonce no longer matching; a reconnect after a reset gets a new boot ID. The device-side boot block is only a witness: the host nonce is what makes the ID new, as NAT-016 requires.
* **Verification criterion for the real run (NAT-043)**: with the collector started before the reboot and nobody present, the archive contains a boot record with a boot ID that did not exist before the run, at least one stage message produced by the loader of that run (the message text contains the image hash or a run counter that only the new image can know), and, in the controlled-fault variant, an exception frame; the USB descriptor capture shows our VID/PID. A run where nothing arrives is inconclusive.
* **What this does not claim**: that the S24 can be brought up this way. The bring-up is exactly what is unknown; USB IDs seen on the host never prove kernel execution (NAT-015).

## 5. Result

* Existing Exynos/DWC3 code is **reference and port material, not drop-in**: no code in the repository drives this controller on this SoC. The authoritative GPL-2.0 sources are the pinned vendor kernel; the upstream sweet engine shows the EP0 engine shape but is Apple-licensed XNU patch code on another SoC.
* The minimal channel is the EP0 control-pull monitor above; a return to S-Boot or Android is explicitly not counted.
* Six child tasks (NAT-039…NAT-043 and this one) are registered with dependencies; NAT-043 is the real-run task that produces the verifiable result.
