## Result in one paragraph

The decision's pass rule is met (analyser `analyze_nat075.py`, unchanged since the commit that holds the decision): chain verdict **PASS**; `root.outcome == "probe-ran-to-exit"` (the project's own probe ran as PID 1 and exited with status 81, as in NAT-068); the kernel text contains `Added memory device md1/rmd1 (01000001/0D000001) at FFFFFFF00897C000 for 0000000093908000`; the return class is **`cap-reset`** (Download Mode `04e8:685d` "SAMSUNG USB" at +177.93 s after the reboot request, inside the decision's +165…+195 s window; it was not the SEC_UPLOAD at about +95 s that the unpetted 83 s hardware watchdog gives). Three things are now measured on the phone that were only designed before: the loader accepts and uses a **4096 MiB window**, XNU boots in it with **16 KiB pages**, and the **bounded watchdog pet** extends a run to the loader's 150 s cap. The reserved md1 region held **no bytes** (the loader's clear plan skips it by design): nothing has been delivered to it yet.

## Established, not established

* Established (native-device):
  - the loader's 4 GiB window (DTB memory nodes merged, the 512 MiB limiters of NAT-073 lifted) works on this phone and its three-span clear completes with the expected byte count;
  - XNU boots with that window and takes **16 KiB pages** (the kernel's page-size rule for memSize > 1 GiB, never run before); free + wired pages add up to the whole 4 GiB;
  - a **reserve-only RAMDisk1** entry in the ADT inside the payload's `kernel_end` (2475720704 B = 604424 × 4 KiB) is registered by the kernel as `md1` at the expected size without any bytes behind it and without disturbing md0, the probe or the boot (the md0 rootless probe boot is the NAT-068 sequence again);
  - the **bounded watchdog pet works**: the hardware watchdog (83 s, which in NAT-046/048 ends an unpetted run in SEC_UPLOAD at about +95 s) did not fire; the run ended by the software cap at +174 s. This is read from the return class, not from a pet counter (the loader sends none): the pet writes are the NAT-074 code, observed here only through their effect.
* Not established:
  - that bytes can be put into md1 (the bulk-OUT receive path does not exist yet: NAT-076) or that the kernel can read a 2.3 GiB image through `/dev/rmd1` (NAT-077's hash probe asks exactly that);
  - the rate of a host-to-phone transfer, so whether 2.31 GiB fits in the cap (150 s of loader time minus the ~27 s to enumerate; the cap can be raised up to the build's 600 s limit, the pet code runs from the loader's tick; this run does not show whether anything feeds the watchdog while the kernel runs free, because the kernel part ended within about 30 s of the jump, so a kernel run longer than the 83 s period is unproven: NAT-071);
  - the RAM left to the kernel: 105775 free 16 KiB pages = 1.61 GiB after the 2.31 GiB reserve and the kernel's own wired memory, because the loader refuses a window above 4 GiB although Android sees 7.06 GiB; whether launchd + dyld + the shared cache fit is open (the cache is read from the ramdisk into the page cache);
  - that Apple's dyld, launchd or any Apple userland runs; the probe is the project's test init. The 16 KiB page size is the kernel's own choice here and has not been checked against Apple userland (A11's own page size is 16 KiB, so it is the expected one).
* Reported deviation: the return came at +177.93 s, 0.2 s above the narrower band the decision predicted from the NAT-068 baseline (+173.2…+177.7 s); the decision's pass rule uses the +165…+195 s window, and the NAT-068 gap between the last 1209:0001 poll and Download Mode (3.8 s) is reproduced. No other deviation from the decision.
