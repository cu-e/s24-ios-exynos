# NAT-030: the payload kernel's start code, run as an instruction-level model

Evidence kind: host-test (an interpreter executes the real payload bytes; an independent CPU model,
Unicorn, cross-checks it). **Nothing here ran on the phone.** Date: 2026-11-10. Owner:
claude-nat029-20261110-krnret.

## Why

NAT-029 read the kernel's return-to-loader contract from the payload bytes: a slot the loader fills, five
assembly checkpoints, 23 C checkpoints, an early-exception report. Native run 007 only ran our own stub at
the kernel copy's entry address; no XNU instruction has executed on the phone. Before the next phone run
(NAT-031) puts a slot-filling loader on the device, this task answers what can be answered on the host:
with the loader's real `boot_args` and the window measured in run 007, does the kernel's own start code
reach `arm_init`, do the five assembly checkpoints stop where NAT-029 says, and can a stub resume them?

## What the model is (and is not)

`kstart_sim.py` decodes the payload's instructions with capstone and executes them: general registers,
NZCV, SP/SPSel, a sparse physical memory over the loader's window (`artifacts/nat-020/build-003/payload.bin`
placed at the segment offsets the loader uses), the system registers the start code touches
(SCTLR/TCR/TTBR0/TTBR1/MAIR/VBAR/DAIF/...), and a stage-1 4 KiB-granule walker for the bootstrap tables the
kernel builds. An instruction it does not implement raises (it never guesses). It has **no** caches, TLB,
cache-maintenance effects, exception model (a fault is reported to the test, it is not vectored), timers,
devices, SIMD/FP registers or timing. It is not S24 evidence and it is not an Exynos model.

Fidelity of the interpreter itself is checked three ways (`test_kstart_sim.py`):

* every instruction word the interpreter executes from the kernel entry to `loader_checkpoint(10)` (208
  distinct words, 34 mnemonics; 20 system/barrier words are skipped) runs alone in both the interpreter and
  Unicorn from 8 random register/flag/memory states each; registers, SP, NZCV, PC and a 64 KiB buffer agree
  in all of them;
* a fixed-seed fuzz of valid base-ISA encodings (data-processing, load/store, branch) compares every word the
  interpreter accepts against Unicorn (the test's seed: 5000 words, 2194 compared across 72 distinct mnemonics, 78
  not implemented by the interpreter (counted, not compared), 2728 skipped, of which 2589 are unallocated
  encodings capstone cannot decode and the rest exclusive/atomic/prefetch forms, UNPREDICTABLE writeback forms
  or words with no aligned test address). Four further seeds of 12000 words each (4 trials per word, run outside the test suite) compared
  5356, 5362, 5344 and 5461 words with 0 mismatches and 0 Unicorn faults (210-249 unimplemented words each).
  The fuzz found real interpreter bugs (shifted-register operands with `asr`/`ror`, extended-register operands
  `uxtb..sxtx`, `negs` with a shifted operand, the `nv` condition, the `sxtx`/`uxtx` register-offset shift);
  they are fixed and the fuzz stays as a regression test;
* uniform sampling reaches some classes too rarely (the test seed drew three `ccmn` words and no `ccmp`, and
  no `csel`), so eight instruction classes are also generated by construction (fixed class bits, random
  fields, 160 words each, 3 trials): `ccmp`/`ccmn` register and immediate, the `csel` family, `b.cond`,
  `cbz`/`cbnz`, `tbz`/`tbnz`, `udiv`/`sdiv`, `madd`/`msub`, and the 64-bit long multiplies. Each class must
  compare more than 40 words with no mismatch and must reach its named mnemonics;
* the full run up to the first MMU-enable instruction is executed in Unicorn too (Unicorn cannot continue past
  the MMU enable in this setup): after the same instruction count the 31 registers, SP, NZCV and the whole
  512 MiB window are identical.

Mutation checks (each a deliberate edit of a copy of the interpreter, run against the tests): a wrong `csel`,
`lsr` or `orr` is caught by the executed-word comparison. A wrong `ccmp` flag order (`nzcv` bits 1 and 0
swapped) is **not** caught by it, because the only executed `ccmp` has `nzcv = 0`; it is not caught by the
uniform fuzz either (no `ccmp` word was drawn). The per-class test catches it (mismatch on a generated
`ccmn x11, x27, #5, gt`). This is why the per-class test exists; an earlier draft of this README claimed the
uniform fuzz covered `ccmp`, which was wrong.

## Established (model level)

1. **The start code reaches `arm_init` with the loader's own `boot_args`.** With `x0 = boot_args PA`
   (`window base + 0x4978000`, layout and fill order read from `loader.c`), EL1, MMU off, DAIF masked, the
   boot CPU runs 8202 instructions and arrives at `_arm_init` (`0xfffffff007431398`) with the MMU on,
   `x0 = 0xfffffff008978000` (the boot_args virtual address), `TCR_EL1 = 0x22a51a251a` (T0SZ = T1SZ = 26, 4 KiB
   granules, IPS 40 bit, TBI0), `SCTLR_EL1 = 0x3454593d`, `MAIR_EL1 = 0x0c08044f00bb44ff`,
   `VBAR_EL1 = 0xfffffff007437000`. The program counter is the physical address until the final `ret` into the
   virtual `arm_init` (identity execution while the MMU turns on).
2. **The bootstrap tables are right for window base `0x9de400000`.** TTBR1 `0x9e15af000` maps
   `0xfffffff007000000..0xfffffff023e00000` linearly to PA `0x9e1400000` (window base + `0x3000000`); TTBR0
   `0x9e15ae000` maps the identity `0x9e1400000..0x9fe200000`. Both are checked on the descriptors and through
   the walker (`mapping_errors`). The loader's physical base must be 2 MiB aligned (the start code builds 2 MiB
   blocks; a misaligned base shifts every kernel address and never reaches `arm_init`; the loader's
   `consider_gap` guarantees alignment). Window sizes `0x10000000`/`0x20000000` and bases `0x9de400000`,
   `0x9dd400000`, `0x80000000` all work.
3. **The five assembly checkpoints stop as NAT-029 says** (slot filled as the loader would, stub PA
   `base + 0x4980000`): `x0 = x1 = 0`, `x2 = 2`, `x3 = N`, MMU off, DAIF masked, `SCTLR_EL1.M` cleared. Stops
   happen after 19, 32, 8129, 8184 and 8200 instructions. The system registers written before each site match
   the source order (VBAR before 2; TPIDR\*_EL0 before 3; TCR/TTBR/MAIR/VBAR before 4; the M=1 write of
   `0x3454593d` is the one right before 5). The kernel never changes the slot.
4. **Resume works for the assembly checkpoints.** After each stop, a model of a resuming stub (poison
   `x0..x3, x9..x11`, restore the SCTLR value the kernel had before the stop path cleared M, write the next
   number into slot `[2]`, continue at `site + 15 * 4`) goes through 1, 2, 3, 4, 5 in order and then to
   `arm_init`, ending in the same register/memory state as the uninterrupted run. No instruction after any
   site reads `x0..x3`/`x9..x11` before writing it (taint tracking).
5. **A C checkpoint is reachable but early ones are hazardous.** With an empty slot the run reaches
   `loader_checkpoint(10)` (the first C checkpoint, `arm_init + 0x468`) after 8453 instructions. Checkpoint 10
   is **before** `cpu_data_init` and `PE_init_platform`, which is where `PE_state.bootArgs` is stored
   (`str x19, [x8, #0xa0]`, `PE_state` = `0xfffffff00724ae88`). With slot `[2] = 10`, `loader_checkpoint` enters
   `loader_jump`, which passes the T0SZ and stub-address guards and then calls `PE_parse_boot_argn("bootcpu")`;
   that reads `PE_state.bootArgs->CommandLine` through a NULL pointer: translation fault at `0x6c`
   (NULL + `offsetof(boot_args, CommandLine)`) in `_PE_parse_boot_argn_internal`, before the stub is entered.
   On hardware the kernel's virtual vectors would take that fault; what they do next is unknown. The first C
   checkpoint after `PE_init_platform` is **11** (`arm_init + 0x48c`); a stub that wants a C stop should use
   11 or later. The C path is not resumable (NAT-029).
6. **Negative controls fail as they should**: a wrong `virtBase` or `physBase` in `boot_args`, a wrong `x0`,
   a window base that is not 2 MiB aligned, a stub PA outside RAM, and a checkpoint number of 0 are each
   detected (never reach `arm_init`, fault, or ignore the slot respectively).

## Not established

* **Every hardware behaviour.** Caches, TLB, the real memory attributes of the window, device-memory
  alignment faults on the S24, the loader's actual jump state, interrupts and timing are outside the model. A
  checkpoint working in the model says the code path is right, not that the phone gets there.
* Whether the kernel's start code behaves with a window above 4 GiB on the SoC's real address map (the model
  only shows the table arithmetic is consistent).
* Anything past checkpoint 10: the interpreter stops at the first SIMD instruction (`movi v0.16b, #0` at
  `_cpu_data_init + 0x10`). `PE_init_platform` (SIMD stores), `gic_v3_irq_quiesce` (MMIO) and the rest of
  `arm_init` are not modelled, so checkpoint 11 and later are known only from the disassembly.
* What the kernel does after a C-checkpoint stop is safe to resume: nothing (not resumable).
* The S-Boot upload-mode protocol, RAM retention across the watchdog reset, any transport for log bytes.

## Consequences for NAT-031 (the first real-kernel stop)

* Fill the slot from the loader (`"XNULDRST"` found by scanning the copied image, three zero words after it);
  keep the kernel's own entry word; jump to the real entry (`br` to the existing handoff target).
* Prefer the **assembly checkpoints 1..5** as the first stops: they need only a stub that runs with the MMU
  off, they are resumable, and the model shows each stop state exactly.
* Resuming at checkpoint 5: the MMU was on at that point, so the kernel's data cache may hold the slot line
  (it read `[2]` at the site). The stub writes `[2]` with the MMU off (non-cacheable, physical) and therefore
  must clean and invalidate that line (`dc civac` on the slot's PA) before restoring `SCTLR_EL1.M`, or the kernel can
  see the old checkpoint number. The model has no caches, so this is a requirement from reading, not a result.
* Do not use C checkpoint 10 as a stop; use 11 or later if a C stop is wanted, after checking in the
  disassembly what `gic_v3_irq_quiesce` touches.
