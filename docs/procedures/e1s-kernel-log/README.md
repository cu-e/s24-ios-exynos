# E1S kernel diagnostic storage (STR034)

This source-only overlay removes two unowned physical diagnostic destinations from the accepted STR014 source. It does not prepare a new complete source/context, rebuild an object, link/package a kernel or establish hardware safety. Original accepted sources, contexts, flags, objects and capsules remain immutable.

Apply `patches/e1s-kernel-log/0001-image-owned-diagnostics.patch` only to a new isolated copy of the exact STR014 tree identified in `fixtures/public/e1s-kernel-log/inputs.json`, after its three accepted source ports. Check the parent manifest and both preimages first, then `git apply --check` and `git apply` inside that copy's own Git root. Exit zero is insufficient: require the two exact postimages. No existing preparer, native caller or consumer descriptor adopts this overlay automatically.

The donor's 0011 log patch maps default-on PA `0x91300000`; 0012's four early markers write PA `0x912ff008`. Neither number establishes ownership in the loader-selected DT RAM window. Donor 0014 moves `e1s_log_init()` into `kernel_bootstrap()` after `vm_mem_bootstrap()`; that call, serial-console append call and their public interfaces remain unchanged. The patch changes only `osfmk/arm64/start.s` and `bsd/dev/e1s_log.c`.

The marker becomes an aligned, nonzero initialized eight-byte slot in writable `__DATA,__data`, referenced by a private assembly label. ADRP/ADD replaces MOVZ/MOVK; each macro still has four instructions, clobbers only x9/x10, touches no stack/NZCV and preserves the same four callsites. Every call is before the existing MMU-enable sequence. PC-relative page addressing works at the loader's physical execution address, provided the image slide preserves page offsets and the linked displacement is in ADRP range. No KVA dereference, guessed PA or new exported symbol is introduced. The explicit initialized section keeps the early marker outside zerofill/BSS; its value must not rely on C initialization, BSS clearing order or log initialization. This is an ordinary image datum, not a cross-reboot persistent record or a proven retrieval ABI.

The ring becomes a static aligned full 1 MiB array with kernel-image lifetime. Ordinary zero-initialized C storage is intended for the linked writable data segment's zerofill/BSS; actual emitted section and extent require future object inspection. Its address is selected only in the existing late C init after VM bootstrap. The header, total/sequence reset, bounds, modulo wrapping, append body and `e1slog=0` behavior are unchanged. Existing pre-init NULL checks continue dropping early text. The buffer is not freed or remapped by this code. The former physical dump instruction is removed; no persistent-log retrieval or concurrent-writer correctness claim is added. Existing locking/overflow behavior is retained.

The pinned `mkpayload.py` retains every nonempty segment's `vmsize`, packs only its `filesize`, and places kernel_end after the maximum complete segment extent. The pinned actual ROOT101 loader source (RAM23b31 + display0689 + owned-loader-log overlay) bounds each segment by `vmsize`, copies file bytes, zeroes `vmsize-filesize` and cleans the entire extent before entry. Thus initialized marker bytes are copied and ring zerofill is reserved/zeroed **if** the final linked image includes those exact extents. ROOT101's overall checker failure is not relabelled as PASS here; its actual source witness is used only for source inspection. Loader-window ownership still depends on genuine DT RAM/reservation metadata; STR034 does not repair or qualify those external facts.

`start.s` builds both V=P and KVA bootstrap block mappings from boot_args physBase/virtBase/memSize. Its full image must fit the mapped full-block extent; rounding memSize down by L2 block size must not cut through either storage range. At the four current marker stores the MMU is still off. At later C ring use normal kernel data mappings must cover the entire 1 MiB array as writable memory. A single-start-address check is insufficient.
