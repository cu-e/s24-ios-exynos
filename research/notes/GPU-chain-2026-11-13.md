## Where the declared dependencies are wrong or stale

1. **KRN-001 is not the real gate for GPU-007.** KRN-001 ("full E1S XNU with supplied SDK") is an obsolete premise: the kernel that
   actually boots iOS userland on the phone is the donor-derived `kernel.no-storage` (NAT-020 build-003 from the STR-041 link,
   SHA-256 `4c9536d8...` before entry stubs) built from the hakios/s24-port tree, not KRN-001's output. GPU-007 has to be built
   into **that** kernel line (or a rebuild of it), not into a KRN-001 kernel that does not exist.
2. **The real host prerequisite is a rebuild of the running kernel with a changed source file.** The running kernel was linked by
   STR-041 from a 1042-row object index with recorded argv/recipes (`worktrees/str-041-e1s-native-link-image-20261110`), and NAT-020
   applied entry stubs to that binary. What has **not** been exercised is the loop "change one source file → recompile that object
   with its recorded recipe → relink → same checks": every kernel change on the NAT line so far was a binary patch or a boot-arg.
   Adding an IOService (the GPU backend) needs that loop. It is not tracked as a task (proposed: KRN-044 below). KRN-043
   (export-checked DEVELOPMENT build) is the nearest existing task and is blocked by the auto-mode classifier, not by a missing fact.
3. **DRV-003 / NAT-003 as gates for GPU-008 are stale.** They are written for a "first native BOOT session"; the native path that
   actually works is the RECOVERY loader with decisions per image (NAT-062..111). GPU-008 should depend on a per-image decision and
   on GPU-007's kernel, not on NAT-003.
4. **GPU-009's dependency on UI-005 is right in substance** (Metal's IOSurface/IOAccelerator contract), but the minimum for a first
   accelerated CA frame is narrower than a full Metal frontend: the donor route is a Vulkan driver + a Metal-on-Vulkan layer
   (apollo: `SweetMetal2` + Turnip; for Xclipse: RADV-xclipse, pinned `fe9b8943`) exposed through an `IOAcceleratorES` service
   whose `MetalPluginName` points at the plug-in. That is GPU-009; it cannot be tested before GPU-008.
5. **Missing step between C1 and C3: the IOAccelerator service.** QuartzCore picks `sw_renderer` because no IOAccelerator matches
   (`IOAccelerator|IOAccelDevice|IOAccelContext` absent from the kernel tree). Publishing one with no working backend would make
   CA try Metal and fail. It must come after GPU-008, never before C1.

## Order that follows from the evidence

1. **C1**: NAT-113 (one run, prepared). Outcome decides the next graphics step:
   * `P1` with an iOS thumbnail → C1 established; go to input (UI-004 touch) and C2 timing.
   * `R1` (surfaces have pixels, panel black) → display copy path (drawLayer→0xfa200000, cache clean, DECON trigger; NAT-070
     follow-up registers).
   * `R0` (surfaces black) → software renderer output; IOSurface lock/unlock/seed handling in MiniIOSurface.
2. **Kernel rebuild line (host, proposed KRN-044)**: record and reproduce the build of the running kernel from pinned source, byte-
   compare where possible; prerequisite for every kernel-side graphics change, including any MiniIOSurface fix from step 1.
3. **GPU-007 retargeted**: integrate GPU-013/015 (done, host) as an IOService in that kernel, behind a boot-arg, off by default;
   power/clock bring-up of the Xclipse from the s24-linux SGPU driver (read-only review first; power/clock writes are a new class of
   risk and need their own decision).
4. **GPU-008**: one native run, clear/copy/triangle from a test program through the GPU-007 user client (C3, first part).
5. **GPU-009 → GPU-010**: RADV-xclipse Darwin winsys + Metal-on-Vulkan + IOAcceleratorES; CA frames through it (C3 complete).
6. **C4**: frame-time measurement over a named workload; only then a 60 FPS claim.

## Proposed registry changes (not applied here; they change other owners' cards)

* GPU-007: replace dependency KRN-001 with the kernel rebuild task (KRN-044, new) and note "target kernel = the NAT line kernel".
* GPU-008: replace DRV-003 with "GPU-007 + a per-image native decision".
* New KRN-044 (host): one-object rebuild loop on the STR-041 index (change a source file, recompile with the recorded recipe, relink,
  rerun STR-041's checks, apply NAT-020's stubs) and a byte-compare of the unchanged rebuild against `kernel.unstripped`.
