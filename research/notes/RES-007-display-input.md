# RES-007: E1S display, STM coordinates and iOS16.5 integration

Reviewed 2026-11-05. Source review and existing DEV-001 capture analysis; no new phone command, MMIO read/write, firmware transfer or Apple component was used. [Coverage](../display-input-coverage.json) and [manifest](../../fixtures/public/display-input-research/source-manifest.json) retain exact scope. Native UI/display/input remain untested.

## Confirmed source defect and correction

The [Samsung STM coordinate declaration](https://github.com/dx4m/android-kernel-samsung-e1s/blob/417484173abc2c4fa93e738ea82ad9f2e84911b1/drivers/input/sec_input/stm_spi/stm_dev.h) places Y's low nibble in byte 3 bits 3..0 and X's in bits 7..4. stm_core.c's stm_ts_coord_parsing reads the corresponding named fields. The [E1S source patch](https://github.com/RNDMBG/iOS-On-S24/blob/c8860decc62c6d6180e609036d027a2997972420/xnu/e1s/patches/0003-e1s-touch.patch) instead gives X the low nibble and Y the high nibble.

UI-006 compiles the **actual extracted post_event** with an explicit host capture shim, not an independently reimplemented decoder. TOUCHREG-001 records the original executable's expected exit 3: 960 of 1,024 synthetic low-nibble/mirroring vectors disagree. TOUCHREG-002 records zero mismatches after the [two-line local correction](../../patches/display-input/README.md). The updated source preparer applies it after the full pinned embedded HakiOS/E1S series, records hashes and rejects patch/pin mismatch. Full kernel compilation and native touch execution remain missing. Original references and historical reports were preserved.

The donor's test_e1s_touch.py checks that strings such as `event[3] & 0x0f` occur; that does not determine which axis receives that nibble. The regression demonstrates why source-presence checks cannot establish the protocol's behavior. Correcting the extraction fixes a code/layout disagreement; hardware packet integrity, firmware variants and actual orientation remain separate questions.

## STM path, identity and lifetime

Pinned s24-linux generated e1s_eur_openx_w01_r13.dts establishes STM over SPI9, 10 MHz ceiling, CS gpp9[3], interrupt gpa1[2], supplies LDO18 I/O and LDO9 analog, and `sec,max_coords = <4096 4096>`. sec_input.c subtracts one to get inclusive maxima 4095; DEV-001 Android input ranges agree. The r13 suffix overrides earlier `fts2ba61y_e1s.bin` with `fts2ba61c_e1.bin` and changes TCLM/AFE metadata. Neither filename is a verified live BYH3 firmware identity; no blob was fetched.

s5e9945-pinctrl.dtsi maps gpa1[2] through EXT_INTA1_OUT2; its binding value 10 is the **SPI index**, so absolute GIC INTID is 42. The donor gic_v3_spi_attach takes an absolute INTID, despite e1s_touch's variable/log wording “SPI 42”. Do not add 32 again. [Historical association](../../fixtures/public/display-input-research/historical-stm-irq.json) finds Android `stm_ts`, gpa1 pin 2, Level and nonzero counters. That supports the GPIO assignment, not correct XNU IRQ delivery. The EINT level-low source policy and active-high parent GIC declaration describe different layers.

The E1S touch driver bit-bangs GPIO rather than implementing the Samsung hardware SPI controller. It writes pin modes, CS and IRQ registers, polls/drains at most 31 16-byte events per iteration and uses a fallback periodic wake. Its SPI transfer function does not report real transfer errors; an ID string of “ok” only excludes all-zero/all-FF bytes. It does not establish version/firmware compatibility, full init/calibration, robust loss recovery, worker cancellation or suspend cleanup. Its state silently promotes MOVE-without-DOWN to DOWN. Those are explicit UI-004/DRV-001 work, not a reason to probe the daily Android pins. GPIO pin ordering, bit timing and rails must be verified before output-driving; do not inherit donor trial pin swaps.

## Physical display versus a framebuffer bridge

The [retail panel source](https://github.com/dx4m/android-kernel-samsung-e1s/blob/417484173abc2c4fa93e738ea82ad9f2e84911b1/arch/arm64/boot/dts/samsung/display_s6e3fae_e1s.dtsi) is s6e3fae at 1080x2340. The generic .17 board overlay references an ERD s6e3hae 1440x3088 panel; it must not select the retail profile. The 60 Hz retail mode already enables DSC, two 540-wide slices of height 60. Deferring advanced GPU compression does **not** mean panel DSC can be ignored during native takeover.

The earlier BSP pin `f85e53cfa5497ead5d78821efbac84e51f37a4e1` s5e9945-drm-dpu.dtsi exposes DECON/DPP/DSIM register/interrupt blocks and DPU DMA SysMMU associations. That source is S8BYG2-related, not proved exact S9BYH3. Native display needs actual clocks/PHY/reset/rails, panel commands/timings/DSC, DMA/cache/IOVA ownership, TE/frame-done IRQ and recovery. Programming an RDMA base or drawing into RAM is insufficient.

E1S 0010-e1s-display.patch is a framebuffer sample and opt-in DECON/DSIM diagnostic probe; it does not program modes or provide an independent display driver. The loader searches FDT nodes by name/size and falls back to 0xFA200000 / 1080x2340 / four bytes per pixel. It does not validate a live pixel format or prove that the selected reserved region is current scanout. No guessed physical fallback becomes a verified mapping. UI-003 must validate ownership, reservation, capacity, format, stride and cache policy before use.

## iOS surfaces, presentation and HID

Embedded HakiOS `d82c64a3a31cd27a0a0afbf6e213e467e44b1b4c` in the S24 pin is the relevant iOS16.5 donor. MiniIOSurface supplies an author-recovered shared-buffer user-client protocol; MiniIOMobileFramebuffer has a 0x46c swap layout, four layers and default logical 1125x2436. Those values are source evidence, not our verification of selected local Apple binaries. The physical S24 panel, logical iPhone profile, normalized touches and crop/scale transforms must remain consistent.

MiniIOMobileFramebuffer copies/scales surface pixels into a boot framebuffer and generates VSYNC notifications by timer. Its SWAP_GPU_MS=500 timeout logs unfinished surfaces but then shows them anyway. SwapWait immediately returns success; SwapSignal/SwapCancel/CancelAll/RequestPowerChange/ChangeFrameInfo also return success without corresponding hardware operations. A full queue may discard a frame after 700 ms while SwapEnd returns success. These policies must not become native completion, cancellation or power evidence. Producer readiness, CPU-copy completion, panel scanout and buffer retirement are separate boundaries. UI-003/005 must reject or defer unfinished frames and retain references until actual completion/quiescence.

Selected drawLayer uses signed additions such as sx+sw and dx+dw before bounds/scaling; MiniIOSurface includes 32-bit plane-size products. These are review targets for overflow/format/capacity validation, not a demonstrated exploit or a completed whole-driver security audit. The [owned layout checks](../../src/platform/display/README.md) use checked arithmetic and subrect admission, but have not replaced the donor path or proved its safety. Multi-plane/compressed/tiled buffers and authenticated cross-process allocation rights remain actual frontend work.

The separately pinned **current** HakiOS source already adds explicit plane-dimension limits, a widened 64-bit planeBytes calculation with allocation-cap rejection, and additional owner-allocation checks. Its framebuffer has a bounded destination-coordinate policy. These are concrete selective-backport candidates for UI-005; compare full preconditions and the selected OS build rather than importing the whole newer tree. The old embedded pin must not be called fixed merely because the current repository has those changes. Current framebuffer code still retains the unfinished-GPU timeout policy, and current input code still shows 0666/shared-queue/drop/copyout behavior in the selected pin.

The embedded redwood input queue has 24-byte records with raw mach_absolute_time, drops the oldest of 512 samples on overflow, advances its head before uiomove success, and creates a 0666 node with unrestricted open. A lost UP can leave a consumer's contact down; multiple readers consume a shared stream. Effective app sandbox access was not assessed. Current HakiOS `87bf4851bcc9cbb24fd79997820aa3661abe4ea5` separately audits these issues and its inject.c shows backboardd virtual IOHID service/digitizer children, normalized contacts, property modes and button-based wake simulation. Current names `/dev/hakios-touch` differ from the embedded `/dev/redwood-touch`; do not mix components by symbol/layout resemblance. A synthetic wake button is not controller wake or panel suspend qualification.

UI-001 defines an explicit **project** 40-byte versioned input boundary with epoch/sequence/nanosecond time and logical cancellation; it is neither donor nor Apple wire ABI. It tests layout/coordinate/loss behavior without emitting HID. UI-005 must translate the selected OS callbacks/timebase, restrict input readers/injection, preserve records on copyout failure, handle partial I/O and consumer restart, and dispatch real cancellations before committing state or stopping.
