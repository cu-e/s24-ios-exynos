# RES-006: E1S Bluetooth transport and iOS donor boundaries

Reviewed 2026-11-05. This is bounded source review plus analysis of an existing DEV-001 Android capture. No new phone command, firmware blob, Apple component, UART operation or radio setting was used. [Coverage](../bluetooth-coverage.json) and [manifest](../../fixtures/public/bluetooth-research/source-manifest.json) preserve exact scope and hashes. Native Bluetooth remains untested.

## E1S provenance and unresolved identity

The [Samsung E1S overlay](https://github.com/dx4m/android-kernel-samsung-e1s/blob/417484173abc2c4fa93e738ea82ad9f2e84911b1/arch/arm64/boot/dts/samsung/e1s/s5e9945-e1s_bluetooth_03.dtsi) selects `bt_kiwi`, compatible `qcom,kiwi`, BT_EN s2mps28_2_gpio[1], BT_WAKE gpc4[0], HOST_WAKE gpa0[3], and WLAN_EN gpb1[3]. Wi-Fi shares 1,350,000/1,025,000 microvolt supplies. Shared rails require coordinated references, not unconditional donor power-off logic. Source revision is not verified as the exact owner's BYH3 build.

The exact `serial_1: uart@11040000` declaration in s5e9945-usi.dtsi has a 256-byte register window, 256-byte FIFO, four-byte access and UART1 gate/ip clocks/pin states. `INTREQ__BT_UART` is SPI index 570, absolute GIC INTID 602. Avoid accidentally matching serial_10. The [sanitized historical association](../../fixtures/public/bluetooth-research/historical-uart-wake.json) finds nonzero Android IRQ counters for 11040000.uart / GICv3 602 and bt_host_wake / gpa0 pin 3. This corroborates the source assignment; it does not test an XNU IRQ handler or read the controller ROM.

Pinned btpower.c uses BT_UPORT=1, Samsung serial wake-peer hooks, regulator/optional clock/enable sequencing and Android HAL SIGIO wake signaling. Its power-on path includes enable-low 50 ms and a WLAN-dependent 100 ms branch; port the full conditions, not two isolated delays. `btpower_get_chipset_version()` returns cached soc_id populated from the BT_CMD_CHIPSET_VERS ioctl argument, not an independent hardware version probe. Kconfig/module selection does not prove the active HAL framing/IBS policy.

The source establishes Qualcomm KIWI family; WCN7850-class is a candidate, not a measured Bluetooth chip/ROM. The selected historical property whitelist provided no matching static vendor BT identity/UART keys. Live SoC/ROM/board ID, patch/NVM identity/digests, initial/operating baud, IBS mode, address provenance and wake policy remain null. Do not guess OnePlus/Mi firmware or power settings.

The [Linux QCA source](https://github.com/gregkh/linux/blob/458c6079fc1d41d564c37679c8ace02cd83ee817/drivers/bluetooth/btqca.c) derives firmware names from controller version and selects NVM using board information. Its WCN7850 branch uses `qca/hmtbtfw%02x.tlv`; this is a conditional filename pattern, not a verified S24 artifact. WCN6390 ht, WCN6855 hp and WCN3990 cr donor files are different profiles. The associated hci_qca.c uses IBS FC wake ACK, FD wake and FE sleep, with a separate wake/retransmit state machine and firmware initialization behavior. Our parser only frames optional boundary bytes.

[iOSPlus10 Bluetooth notes](https://github.com/akshaynexus/iOSPlus10/blob/146e889430bab755329dde7104cc0fa002f44bfb/patches/xnu/README-bluetooth.md) have earlier unrun sections and later October 27 evidence. Read both. Its kernel PF_SYSTEM control socket, ADT/registry transport and BlueTool XPC stand-in are more relevant than assuming a generic IOBluetoothIOUserClient path. [Bergamota transport notes](https://github.com/ry-diffusion/bergamota/blob/37a7a7a917fc09945ed2f7d1ae68b84d4525b4cb/docs/BT_IOS_TRANSPORT.md) distinguish the default `.sk.` Skywalk endpoint from an alternate plain control stream. Neither establishes the exact selected iOS16.5 contract. BT-004 requires explicit local components and authenticated lifecycle handling.

Apple/Broadcom and QCA vendor opcode namespaces collide (e.g. QCA fc48 changes baud). Forwarding Apple commands blindly is unsafe and fake success is not semantic implementation. The iOSPlus10 0337 notes describe padded vendor completions, fabricated status zero for selected fd3c/fce9/fce2/fd48/fd47 commands, rewriting 0x2007 controller error 0x0c to status zero / 0 dBm, and rewriting residual 0x0c6d errors. That can advance daemon initialization while misrepresenting controller behavior. Our model preserves raw replies and does not copy this policy. Per-command adaptation must establish truthful supported capabilities, return layouts and effects.

[Apollo injection source](https://github.com/aTechGeekDev/ios-apollo/blob/b5ac6999c65b03c432139af99cf47ab84eefd4e8/userland/bt-inject/sweet_bt_inject.c) checks kernel readiness before answering ready, but also patches exact executable instruction offsets and emulates BlueTool behavior. These are useful boundary examples, not reusable version-independent offsets. Its README says the CPU does not suspend and panel/GPU remain powered with screen off, despite the linked post's broad sleep claim. Pairing, profile traffic, true suspend and durable power control require different measurements. An author's percentage is not hardware acceptance coverage. Never execute donor USERDATA erase/install instructions on the daily S24.

Apollo's root MIT license was reviewed; component notices still apply. Bergamota's selected root tree has no LICENSE/COPYING or explicit global grant; resolve rights before implementation reuse. Samsung/Linux GPL and other donor components retain their own licenses. No donor implementation or firmware is incorporated by BT-001; its C model is independently authored.

## Wire semantics and host result

The official [HCI UART transport specification](https://www.bluetooth.com/wp-content/uploads/Files/Specification/HTML/Core_v6.3/out/en/host-controller-interface/uart-transport-layer.html) defines indicators 1–5 and framing by packet length. The [HCI functional specification](https://www.bluetooth.com/wp-content/uploads/Files/Specification/HTML/Core_v7.0/out/en/host-controller-interface/host-controller-interface--hci--functional-specification.html) describes credits, opcode-zero credit notifications, raw Command Complete return parameters and Command Status accepted/rejected behavior. These references establish framing rules, not the S24 controller's Core version/features.

BT-001 implements [bounded H4/initialization models](../../src/platform/bluetooth/README.md). ASan/UBSan passed 20,000 deterministic mutation/control attempts; four ARM objects are compile-only, not an XNU link or runtime. Stop/timeout retain uncertainty; a local epoch cannot flush late UART replies. Native DMA/UART drain, IBS sleep, firmware authentication/boot and actual teardown are missing BT-003 work.

## Community coverage and concrete continuation

The Bluetooth archive search returned 15 titles, of which four bodies and three comment sets were read. October 27 OnePlus10 reports newer Wi-Fi/Bluetooth progress than the earlier Wi-Fi review's October 24 post; selected comments still exclude AirDrop/cellular. The A52s post reports Bluetooth but selected comments provide a video and no usable public source link. No private contact was made. Mi10T Pro points to Apollo; the November 5 Pixel7 post leaves Wi-Fi/BT unplanned. That author's activation-ticket explanation is speculation, not proof that our modem path is impossible. Archived comments and keyword searches are incomplete; no internet-wide absence claim follows.

BT-003 implements real E1S UART/power/firmware and links against pinned XNU after KRN-001 inputs exist. BT-004 implements the selected iOS16.5 frontend. BT-002 then qualifies BR/EDR and LE discovery, secure pairing/bonds, BLE GATT/HID and lifecycle under the native gate. BT-005 additionally measures A2DP/AVRCP/HFP audio routing, reconnect/sleep, power and Wi-Fi coexistence with controlled peers. AirDrop, LE Audio and privacy claims require their own verified support. These tasks preserve current host-only authorization and daily Android.
